## Behaviour and retention

- Super Admin alone can delete from the bottom of **Edit member**, separated from Save. The modal uses the requested copy and an initially empty input. The complete `Delete {stored lastName}'s record` phrase must match exactly, including whitespace, Unicode representation, punctuation and case. Pasting is allowed. The server checks the current surname and version again under the existing fresh-authority/management transaction lock.
- Cancel receives initial focus. Cancel/Escape/backdrop dismiss before submission; inside clicks do not. Focus traps and returns. Submission is guarded against duplicates, cannot be dismissed while pending, and retains the modal/input with a safe error on failure. A stale record requires reload/review. Success navigates to Members; no Restore/Undo exists.
- `member.deleted_at` is a **soft-deletion marker**, not erasure: the full private member row, creation key/digest, original applications/answers/decisions, immutable associations, existing notification metadata and audits remain stored internally. Normal directory/search/match/detail/edit/profile services exclude deleted members; they must also be excluded by A06's future research-group selectors. No retention period or irreversible personal-data destruction is claimed. A separately approved retention/erasure policy is still required.
- Deletion increments the version, clears the leadership identity FK and writes generic **Deleted member** audit metadata (actor, server timestamp, target ID). If linked, a safe ID-only **Unlinked leadership profile** event is included. All writes are atomic; audit failure rolls everything back. The independent profile's content/visibility, separate administrator/account/session and source records are untouched. No new email or notification is generated.
- Partial normalized-email uniqueness applies only to nondeleted members, including Inactive ones. A fresh Add uses a **new ID and request key**; a deleted record's original addition key is refused. Historical applications show that their associated member was deleted; approval replay and reconciliation cannot restore or reassign that immutable history, even after a fresh member uses the email. Pending/unassociated historical reviews with stale deleted-member acknowledgements conflict; a fresh review may establish a distinct identity.
- Privacy backdrop dismissal uses native dialog bounds and requires the pointer interaction to begin and end outside. Inside/padding clicks stay open. Close/Escape/focus/background inertness/scroll lock and all entered values/consent remain. The shared visible development callout, placeholder subheading and explanatory disclaimer are removed; the existing title and **exact Lorem ipsum** remain. No invented policy, consent/version update or return-to-form link. The form's existing test-information warning and noindex remain; **final privacy/retention wording is still a public-launch gate**.

## Migration and operations

**`drizzle/0006_member_deletion.sql`** adds the nullable timestamp and deleted-profile check and replaces the email unique index with a partial index. It backfills/deletes no records. It is registered in the existing Drizzle journal and uses the unchanged explicit `npm run admin:migrate` convention; build/start do not run migrations. No new env/dependency, migration runner, deployment workflow or external setting is introduced.

An owner-authorized operator must review/apply `0006` (and earlier migrations) on the **isolated Preview database before this code is used**, through the established migration process. Missing schema fails closed. Do not run destructive tests on Neon/hosted databases. After deleted/re-added emails exist, reverting to the old unconditional unique index is unsafe; retain the migration and use a forward correction. No live migration was run here.
