## Current approval and reconciliation contract

Super Admin approval rechecks fresh authority and pending/unexpired eligibility under the existing management/application transaction locks. Expiry eligibility and recorded decision time share one database instant; the new join date derives from that same UTC instant. A successful transaction records the final decision/reviewer/server timestamp, Active membership, immutable application association, safe audit events and one version-2 approval notification intent. Any required database failure rolls **all** of those changes back. Provider requests remain asynchronous and independently disabled; provider rejection cannot undo approval/membership.

New members copy the original first/last name, normalized email, career stage and research interests. Status is Active; join date is the **approval timestamp's UTC calendar date**. Optional phone/affiliation/notes remain blank under the existing schema. Motivation, consent, original answers and private review notes stay on the application. Membership grants no administrator account/session/dashboard access and publishes no leadership profile.

A matching normalized email requires an explicit acknowledgement of the displayed Member ID and current version. Inactive membership additionally requires explicit reactivation acknowledgement; only status/version/update time change. Preserve all existing profile fields, notes, links and original join date. No name-only merge. Missing acknowledgement, changed/vanished match or stale version conflicts and requires refreshed review. Normalized-email uniqueness and one-association constraints remain authoritative; concurrent manual addition cannot produce a second identity.

Repeated/concurrent successful approvals return the same associated member without another Member, association, audit, note overwrite or notification. Rejection and expiry remain final; late pending applications cannot approve, including after lock waits. A later manual member deactivation is not undone by replaying an already completed approval. A05.5.1 additionally refuses replay/reconciliation when the associated member has been deleted; immutable history is never restored or reconnected.

New approvals show **View associated member**, with no separate Add/convert step. Historical approved records without associations show **Add member** reconciliation on the review itself. It uses the same member-establishment service, existing-match/reactivation safeguards and **original approval date**; preserves the original application/decision and generates **no new approval notification**. Historical data is not bulk-converted. Old `/admin/membership/members/new?application=<UUID>` bookmarks redirect to the protected application review. Legacy conversion request bodies with editable source/status/date fields are rejected; reload the current form.

## Usability and privacy

- Manual member actions/headings/confirmations/empty states use **Add member**, never Invite member; manual addition sends no invitation. Existing database identifiers and audit key **Created member** remain compatible.
- Add/Edit and approval/reconciliation checks run automatically after **350ms** of inactivity. Require a complete email or at least two characters in both names; normalize email, exclude the edited Member ID, keep private values in authenticated POST bodies and retain the existing server rate limit. Abort old requests and associate results with the exact query instance, including A→B→A; stale responses cannot replace current results. Loading, matches and honest lookup failure are visible; values are retained. Namesakes remain valid and submission repeats authoritative checks.
- Approval/reconciliation confirmation waits for the current lookup to succeed. Existing-member and Inactive reactivation checkboxes are required; a changed record resets acknowledgement. After a stale/error response, close/reopen or refresh the review to obtain a current result. Manual Add/Edit can still attempt a save after lookup failure; the database enforces uniqueness and no match result is implied.
- `/join` enhances the existing `/privacy` link with a native modal dialog, shared policy content, accessible title/Close control, focus entry/Tab wrapping/Escape/focus return, inert background, scroll locking and mobile overflow. The portal is outside the disabled form fieldset, so Close remains usable when applications are unavailable. Opening/dismissing never submits, checks consent or resets values. Without JS/unsupported dialog support, the original link opens `/privacy`; native form submission stays intact. Modified link clicks keep normal navigation behavior.
- The independent `/privacy` page has no return-to-membership text link. [A05.5.1](reviews/05-5-1-member-deletion.md) subsequently removes visible placeholder messaging around the retained Lorem ipsum and adds backdrop dismissal; the policy is still unapproved. No legal content/version/consent change or launch approval. Public form layout, original routes, fonts, NOSEE colours and MingCute/currentColor policy remain intact. No Radix/admin dependency enters public bundles.
