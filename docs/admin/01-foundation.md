## 1. Select safe backend and security foundation (not a fake login)

- Review current repo, deployed environment **capabilities without reading or exposing secrets**, and official compatibility docs before adding libraries. The PRD prefers **PostgreSQL**, with a mainstream ORM and server-side authentication; verify exact stable versions compatible with Next 16.4/React 19/Node 24 and Vercel. Choose the **minimum maintainable** dependency set. Document the decision in a short `docs/admin/architecture.md` with required owner provisioning/env variables; no paid provider, account connection, credentials or deployment setting changes without owner approval.
- Implement a genuinely **server-authorised, fail-closed admin boundary**: unauthenticated requests cannot read any private page/data/action; a member/application record must **never** grant login. No public admin sign-up. Secure session cookies, logout and CSRF-safe mutation patterns; rate-limited sign-in or an appropriately documented equivalent. No insecure shared default password or query-string/localhost role bypass.
- Supply migrations/model(s) for administrator identity, assigned access role and optional research-group scope, audit-ready timestamps; use approved values `super_admin`, `editor`, `research_group_lead`. Group Leads are scoped to their assigned research group as approved; no access via manually changed URL/API/action parameters.
- **First Super Admin bootstrap (required in A01):** Implement a **one-time, server/CLI-only** `npm run admin:bootstrap` command (not a pretend existing command, public setup URL or signup form). After database migrations, a person with authorised operational access runs the command against the intended environment. It securely prompts for first name, last name, email and a strong password **using masked interactive input**, creates the initial `super_admin` with a vetted password hash and audit timestamp, and never prints/stores the plaintext password. Require an actual interactive privileged session; do not accept the password in shell arguments, commit it to `.env`, or generate any hardcoded demo credentials. The command must refuse to bootstrap when a Super Admin already exists, including concurrent invocation safety; repeated execution cannot elevate an existing account. Document the exact prerequisites, command and first-login URL in `docs/admin/architecture.md`. No email delivery dependency for bootstrap.
- **Preview versus production:** Keep preview-only Super Admin, Editor and Research Group Lead identities **in an isolated preview database**; never reuse real identities/passwords, preview admin sessions, or fixtures in production. Real production bootstrap occurs separately when its DB and deployment are provisioned and authorised. Subsequent administrator onboarding is an invite/role-management workflow planned under A02 (`Settings → Administrators`), not repeated bootstrap or self-registration.
- If managed DB/auth infrastructure isn't configured, **fail closed** and explain the exact owner setup needed; don't expose a public mock dashboard as an authentication substitute. Use local ephemeral test fixtures to screenshot roles. Do not fake persistence or email delivery.

## 2. Implement the admin design foundation, not the whole CMS

- Create the `src/app/(admin)/admin/` app boundary and private layout plus a deliberate sign-in route. Build the **Shopify account-settings-inspired shell**: restrained sidebar, logical primary navigation, active state, compact top bar/account menu, quiet borders/panels, meaningful page headings, responsive mobile navigation and real empty/loading/error states. Use NOSEE typography/brand green and existing tokens without changing the public site.
- Use **shadcn/ui** primitives in a small, consistent library; **MingCute is the only general-purpose icon pack**. Replace shadcn-generated Lucide imports, use actual official MingCute exports, choose closest official substitute if needed; minimize icons beyond sidebar. Every icon inherits relevant label/control text `currentColor` across normal/hover/focus/selected/disabled, including dark backgrounds. No random decorative uppercase/over-explanatory cards.
- Implement **working** `/admin` role-aware Overview (no invented numbers), `/admin/settings/general` current-user account details (first/last name, email, photo if secure upload is actually provisioned, account security actions as supported), sign-in/sign-out and the role-based navigation. A form must save through an authenticated, server-authorised, validated action or remain clearly unavailable; never show fake success. Don't add global organisation settings.
- Scaffold only the **minimum route boundaries/authorization logic** needed for future `Membership`, `Research`, `Publishing`, `Website` and settings destinations. Modules not yet implemented must not pretend to work; don't create dozens of empty page files solely to mirror the TRD tree. Document where each planned page lands using the approved tree.
- Visibility: **Super Admin** sees Overview, Membership, Research, Publishing, Website, Settings General/Administrators/Activity log. **Editor** sees Overview, Publishing, Website, Settings General. **Research Group Lead** sees scoped Overview, own Research group, Settings General. The nav may clearly mark unopened modules, but **backend permissions must be tested independently from whether a link appears**.
- The app's future special rules are binding: Research Group Lead may publish their assigned group's content and fully edit its approved-member associations; editors cannot see private membership. **Leadership profiles** are independent of membership and live directly under Site content (no About editor). The Gallery supports standalone caption-required photos and caption-optional albums; Homepage News/Events/Research records populate automatically; Publications use DOI-first metadata lookup with editable fields. About copy, Contact, shared content and public monitoring dashboards remain code-managed; the Monitoring dashboards admin destination is reserved and empty. **Do not implement those future editors yet**.
