## Scope and data boundary

Exactly four events: applicant acknowledgement on submission, administrator alert on submission, applicant approval and applicant rejection. No expiry/marketing/newsletter mail, new invitation workflow, Email Delivery page or generic operations dashboard. Application approval never creates a Member/login/public profile; A04 conversion remains explicit. Public receipt now says it confirms receipt, **not email delivery**. Privacy placeholder content is unchanged and is not approved launch wording.

Submission/decision writes its notification intent in the **same PostgreSQL transaction** as the application and existing safe audit. Failed intent persistence rolls everything back; provider calls occur later, outside that transaction, so a provider failure cannot invalidate an application/decision. Unique `(application_id, kind, recipient_key)` prevents duplicate events. Each explicitly configured admin recipient gets an independent job; applicant jobs resolve their immutable original application email/name rather than storing copies. An admin recipient matching that applicant is held, never used to send the internal alert. Historical applications are not backfilled. No decision notification on invalid/repeated/expired decisions or Member conversion.

`0004_membership_notifications.sql` adds only the outbox and singleton dispatch gate, constraints/indexes; it does not modify/backfill existing identities, sessions, invitations, applications, Members or audit history. Apply through the established explicit `npm run admin:migrate` on an **owner-authorized isolated Preview database** after reviewing the SQL. No build/start migration. This task applied migrations only to disposable loopback PostgreSQL. Retain additive data/history on rollback; disable the worker before rolling back application code.

Jobs retain IDs/kind, state/attempt/timing/claim metadata, template version, activation hash, payload hash, provider acceptance ID and safe issue code. Approved jobs snapshot sender/origin and only the necessary explicit admin recipient. No rendered body, motivation, research answers, internal review note, applicant email/name copy, API key or invitation token is stored in the outbox. Templates use only the original first name and, for admin alerts, an authenticated application-detail link. Admin alerts contain no applicant answers/contact information. Activity logs have System actor, generic target ID and status transitions only, never addresses or message/provider bodies.

## Server-only configuration — OFF by default

| Variable | Exact requirement |
| --- | --- |
| `MEMBERSHIP_EMAIL_ENABLED` | Exactly `true` to permit prospective queueing/processing. Defaults off; independent of invitations. |
| `MEMBERSHIP_EMAIL_FROM` | Bare verified sending-domain email; app adds `NOSEE <…>`. No display-name/header input. |
| `MEMBERSHIP_EMAIL_ADMIN_RECIPIENTS` | Explicit comma-separated **1–10 unique** valid addresses, trimmed/lowercased. Owner approves each recipient's access to application notifications; never infer the administrator directory or fall back to an applicant. |
| `MEMBERSHIP_EMAIL_START_AT` | Explicit owner-approved prospective ISO 8601 instant with timezone, preferably UTC `…Z`. Events before this instant stay held. Use a **new future cutover** for a new activation. |
| `RESEND_API_KEY` | Existing server-only Resend sending-access key restricted to the verified domain; never `NEXT_PUBLIC_*`. |
| `ADMIN_ORIGIN` | Existing exact **HTTPS** application origin, no path/trailing slash; matches auth and approved Preview hostname. Local HTTP auth works, but membership sending intentionally remains unavailable there. |
| `MEMBERSHIP_EMAIL_WORKER_SECRET` | Independent cryptographic bearer secret, **32–256 non-whitespace characters**. Not the expiry `CRON_SECRET`, API key or auth secret. Needed for HTTP worker; CLI uses trusted process/DB access. |

Missing/invalid required mail configuration returns disabled/unavailable and makes **no provider request**. Submission/review continue with held intents. HTTP without a valid worker secret fails closed. Empty values in [`.env.example`](../../.env.example) are documentation, not usable credentials. Never print secrets, recipients, private applicant values or mail bodies into logs/commands shared with others.

### Prospective activation and backlog policy

1. Keep membership disabled while reviewing code/SQL, verifying the sender domain, approving recipients and arranging isolated test inboxes. Domain/DNS/Resend/Vercel changes and real sending require separate owner authorization.
2. On the authorized isolated Preview only, set a **future** cutover plus approved sender/recipients/origin/key and worker secret in the private secret store. Restart/redeploy through the owner's normal workflow; this task does not perform it. Enable for new synthetic submissions after the cutover and verify all four inbox messages before any broader activation.
3. Events recorded disabled, malformed or before cutover are **held permanently** by normal workers, with no next attempt. Enabling never promotes them; no historical export/backfill/replay endpoint exists. Jobs snapshot an activation hash of normalized sender, origin, sorted recipients and cutover. Changing any of those pauses older queued jobs and never reroutes them to a new recipient; API-key rotation alone preserves the same activation/key/body. Disabling pauses workers immediately; already in-flight requests can still be accepted. Previously approved queued work can resume under the **same** activation, so use a new future cutover when reactivation must exclude that work.
4. Separately approved backlog replay is **not implemented or authorized**. An operator must first reconcile uncertain outcomes/provider records, review application status/recipient/content/privacy/age and decide which events may be recreated through a separately reviewed migration/tool. Never reset attempts, recycle uncertain events with fresh idempotency keys or promote every held row. No blind replay beyond provider retention.

## Worker and reliability contract

- HTTP: `GET /api/internal/membership-emails` with `Authorization: Bearer <MEMBERSHIP_EMAIL_WORKER_SECRET>`, **server-to-server header only**. Do not put it in a URL. A dashboard cookie is insufficient. Responses are private/no-store: 401 wrong authorization; 503 missing secret/disabled configuration/unconfirmed persistence; otherwise safe `enabled`, `processed` and `outcome`, without recipients/body/provider ID.
- Operator CLI: `npm run membership:mail`, Node 24 with intended server env loaded securely (`.env.local` ignored, injected values take precedence). One invocation processes **at most one** due message. Exit 2 when disabled, 1 for processing/persistence failure, 0 for an enabled idle/rate-gated/completed invocation. JSON outcome `accepted` means provider acceptance only. CLI is privileged server access, not an admin UI retry bypass.
- **No schedule installed.** Owner must later configure an authenticated runner, retry failed invocations, monitor safe outcomes/backlog and verify unattended execution. Invoke repeatedly to drain independent jobs. A once-per-minute schedule starts at most one message/minute and cannot keep up with sustained higher traffic; choose approved cadence/capacity accordingly. Do not add a public scheduler/cron endpoint or log its secret. Expiry uses its existing independent worker/secret and also remains unscheduled.
- PostgreSQL transaction lock `4631004`, row claiming/`SKIP LOCKED`, random claim token and 120-second lease serialize claims across processes. Provider calls run outside locks; an old response cannot overwrite a newer claim. A process resuming after prepare/commit rechecks the lease/window immediately before starting the provider request. Interrupted claims become **unconfirmed**, never assumed accepted/failed. Application/management locks remain unchanged.
- Shared database gate limits membership **starts to one/second** across workers. This is an application policy, not a claim about the account's current Resend quota; invitation traffic can share the provider account. HTTP 429 honors seconds/HTTP-date `Retry-After` (bounded 1–86,400 seconds, invalid defaults 60) and pauses all membership starts for at least the retry delay. Runtime provider/account quotas still require owner verification.
- Eight-second hard deadline covers request and response decoding, including a request implementation that ignores abort. One provider call per invocation; fetch never redirects. Five attempts maximum with 60/300/1,800/7,200-second backoff. Known terminal rejection stops as failed; rate limits can retry. Network/timeout/409/5xx/malformed acceptance remain unconfirmed. Prior uncertainty is retained even if a later request is rejected.
- Stable `nosee-membership/<job UUID>` key and identical canonical body for every retry. SHA-256 payload hash detects changed template/source/snapshot before resend and stops it for review; template version 1 is immutable for existing jobs. Do not edit its wording for pending retries without a separate version/migration policy.
- Resend's documented retention is **24 hours**. We stop retries at **23 hours from the first attempted claim**, leaving a conservative margin; attempt exhaustion, interrupted claims outside the window or a delay reaching the cutoff stop permanently. No UI retry button or automatic new key exists. Reconcile unconfirmed messages with the provider before any separately approved action.
- Only valid HTTP 200 acceptance ID records **Accepted by provider — inbox delivery not confirmed**. No delivery webhook/status polling/tracking exists. Super Admin application detail shows safe per-event state, attempts, next eligible attempt and paused/interrupted conditions. No recipient addresses, provider response text or internal notes enter that summary. Editor/Lead/anonymous access is denied on server reads and APIs.
